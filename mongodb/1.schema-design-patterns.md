# MongoDB Schema Design Notes

---

# 1. Inheritance Pattern

## What is it?

The **Inheritance Pattern** is used when multiple document types share many common fields but also have some unique fields.

Instead of storing completely different document structures, we create a **common base structure** and allow each document type to have additional fields.

Example:

```
Book
├── product_id
├── description
├── authors
├── publisher
├── language
│
├── Printed Book
│   ├── pages
│   ├── isbn10
│   └── isbn13
│
├── Ebook
│   └── eformats
│
└── Audiobook
    ├── narrator
    └── length_minutes
```

Every product shares the common fields while keeping its own specialized fields.

---

## Why use it?

* Keeps schema consistent.
* Makes queries easier.
* Avoids duplicated field names.
* Easy to add new product types later.
* Allows different document shapes in the same collection.

---

## How Aggregation Pipelines Maintain It

Aggregation pipelines are often used **once** (or occasionally) to migrate old documents into the new inheritance structure.

They standardize documents without manually editing every document.

---

### Example 1 — Standardizing Documents

Pipeline used:

```
$project
```

Purpose:

* Rename fields

  * `desc` → `description`
  * `details` → `description`
* Convert

  * `author` → `authors` array
* Add missing

  * `product_type`
  * `product_id`
* Keep common fields only

Example

Before

```js
{
    desc: "...",
    author: "John"
}
```

After

```js
{
    description: "...",
    authors: ["John"],
    product_type: "Unspecified"
}
```

Then

```
$merge
```

writes the transformed documents back into the same collection.

---

### Example 2 — Cleaning Data

Pipeline used

```
$match
```

Finds documents where

```
product_type = "Unspecified"
```

and

```
length_minutes >= 0
```

These are clearly audiobooks.

Then

```
$set
```

updates

```js
product_type = "audiobook"
```

Finally

```
$merge
```

replaces the old document.

---

## Operators Used

### `$project`

Creates a new document shape.

Used to rename fields and choose which fields to keep.

---

### `$ifNull`

Provides fallback values.

Example

```js
description:
    desc
    OR description
    OR details
    OR "Unspecified"
```

Useful when older documents have different field names.

---

### `$set`

Updates or adds fields.

Example

```js
product_type = "audiobook"
```

---

### `$match`

Filters only documents that need updating.

---

### `$merge`

Writes transformed documents back into the collection.

---

# Takeaway

Aggregation pipelines help **maintain the inheritance pattern** by

* standardizing field names
* converting old schemas
* filling missing fields
* classifying document types
* saving the cleaned documents back into MongoDB

# 2. Computed Pattern

## What is it?

The **Computed Pattern** stores values that are expensive to calculate repeatedly.

Instead of computing every query,

```
Raw Data
        ↓
Aggregation
        ↓
Computed Result
        ↓
Store or Return
```

Examples

* average rating
* total sales
* number of reviews
* total revenue
* monthly statistics

---

## Why use it?

Without Computed Pattern

Every request must recalculate from thousands or millions of documents.

With Computed Pattern

Compute once → reuse many times.

Much faster.

# Roll-up Operations

A **roll-up** summarizes many documents into fewer summary documents.

Example

Thousands of books
↓
One summary per product type

Instead of
```
1000 book documents
```

You get
```js
{
    product_type: "ebook",
    count: 420,
    averageAuthors: 2.4
}
```

Roll-ups reduce large datasets into useful statistics.

---

## Example 1 — Books Roll-up

Pipeline

```
$group
```

Groups documents by

```js
product_type
```

Inside each group

### `$sum`

```js
count: { $sum: 1 }
```

Counts how many books exist.

---

### `$size`

```js
$size: "$authors"
```

Counts authors in each document.

Example

```
["John","Mike","Tom"]
```

↓

```
3
```

---

### `$avg`

```js
$avg
```

Averages the author counts.

Result

```js
{
    _id: "ebook",
    count: 1,
    averageNumberOfAuthors: 3
}
```

---

## Example 2 — Review Roll-up

Pipeline

```
$bucket
```

Groups reviews into rating buckets.

```
1-star
2-star
3-star
4-star
5-star
```

Grouped using

```js
review.stars
```

Each bucket computes

```
count
```

Number of reviews

and

```
user_id
```

Array of users who gave that rating.

Result

```js
{
    _id: 5,
    count: 20,
    user_id: [101,205,312]
}
```

Meaning

* 20 reviews gave 5 stars
* These users wrote them

---

## Operators Used

### `$group`

Groups documents together.

Example

```
All ebooks
↓

One summary
```

---

### `$sum`

Counts documents or totals values.

---

### `$avg`

Calculates averages.

---

### `$size`

Returns the length of an array.

---

### `$bucket`

Groups values into ranges (buckets).

Example

```
Stars

1
2
3
4
5
↓
Buckets
```

---

## How Aggregation Pipelines Maintain the Computed Pattern

Aggregation pipelines generate computed summaries from raw data.

### Example 1 — Books

Pipeline computes:

* total books per `product_type` (`$group` + `$sum`)
* average number of authors (`$size` + `$avg`)

Result:

```js
{
    _id: "ebook",
    count: 150,
    averageNumberOfAuthors: 2.3
}
```

This is a **roll-up summary** of many book documents.

---

### Example 2 — Reviews

Pipeline groups reviews into star-rating buckets using `$bucket` on `review.stars`.

For each rating it computes:

* number of reviews (`count`)
* list of users who gave that rating (`user_id` array)

Result:

```js
{
    _id: 5,
    count: 42,
    user_id: [5178, 2034, 1190]
}
```

This summarizes many review documents into one document per rating, making reporting and analytics much more efficient.


# Extended Reference Pattern

## What is it?

The **Extended Reference Pattern** stores **selected fields from another collection** inside a document to **avoid expensive `$lookup` (JOIN) operations**.

Instead of fetching related data every time, we duplicate only the fields we frequently read.

---

## Why use it?

* Avoids expensive `$lookup` (JOINs).
* Reduces read latency.
* Fewer database round trips.
* Faster read performance.
* Useful for read-heavy applications.

---

## Example

Without Extended Reference

```text
reviews
    ↓
$lookup
    ↓
books
    ↓
users
```

Every query needs to join multiple collections.

---

With Extended Reference

```js
{
    review: { ... },

    product: {
        sku: 123,
        title: "MongoDB Basics",
        product_type: "ebook"
    },

    reviewer: {
        user_id: 25,
        username: "John"
    }
}
```

Everything needed for displaying/searching the review is already inside the review document.

No `$lookup` needed.

---

## When should you use it?

Use it when:

* Related data is read frequently.
* Read performance is more important than storage.
* The duplicated fields change rarely.
* Only a few fields from another collection are needed.

Good examples:

* Book title
* Product type
* Username
* Category name

Avoid duplicating fields that change often.

---

## Drawback

**Data duplication.**

If the original document changes, the duplicated fields must also be updated.

To minimize this:

* Duplicate only necessary fields.
* Choose fields that rarely change.
* Decide whether updates must happen immediately or can be done later (eventual consistency).

---

# How Aggregation Pipelines Maintain the Extended Reference Pattern

Aggregation pipelines can be used to **add extended references to existing documents**.

---

## Example

Pipeline uses:

### `$lookup`

Joins related data from another collection.

Example:

```text
reviews
    +
books
```

Brings book information into each review document.

---

### `$project` / `$set`

Keeps only the required fields.

Example:

```js
product: {
    sku,
    title,
    product_type
}
```

Instead of embedding the whole book document.

---

### `$merge`

Writes the updated review documents back into the collection.

---

## Example from the bookstore

Pipeline:

* Uses **`$lookup`** to get book information.
* Embeds only `title` and `product_type` into the review's `product` subdocument.
* (Similarly, user information like `user_id` and `username` can be embedded from the `users` collection.)
* Uses **`$merge`** to save the transformed documents back into the `reviews` collection.

Result:

```js
{
    review: {
        stars: 5
    },

    product: {
        sku: 12345,
        title: "MongoDB Basics",
        product_type: "ebook"
    },

    reviewer: {
        user_id: 25,
        username: "John"
    }
}
```

Now searches can return all required information from a **single review document**, avoiding repeated `$lookup` operations.

---

# Operators Used

* **`$lookup`** → Retrieves related documents from another collection.
* **`$project` / `$set`** → Keeps or reshapes only the needed fields.
* **`$merge`** → Saves the transformed documents back into the collection.

---

# Takeaway

The Extended Reference Pattern improves **read performance** by embedding a small amount of frequently used data from other collections into the main document. Aggregation pipelines help **apply and maintain** this pattern by using **`$lookup`** to fetch related data, **`$project`/`$set`** to embed only the required fields, and **`$merge`** to update the existing documents.
