# MongoDB Indexes (Backend Notes)

## What is an Index?

An **index** is a separate **B-tree** data structure that stores field values in sorted order along with pointers to documents.

Without an index:

```js
Video.find({ owner: "Ken" })
```

MongoDB performs a **Collection Scan (COLLSCAN)**:

```text
Video1 → Video2 → Video3 → ... → Video10,000,000
```

Time Complexity:

```text
O(n)
```

With an index:

```text
B-tree

↓

Find "Ken"

↓

Jump directly to matching documents
```

Instead of scanning millions of documents, MongoDB traverses the tree and directly fetches matching records.

---

# Single Field Index

Indexes one field.

```js
db.videos.createIndex({
    owner: 1
})
```

Optimizes:

```js
Video.find({
    owner: userId
})
```

Good for simple equality or range queries on one field.

---

# Compound Index

Indexes multiple fields in a specific order.

```js
db.videos.createIndex({
    owner: 1,
    createdAt: -1
})
```

Perfect for:

```js
Video.find({
    owner: userId
}).sort({
    createdAt: -1
})
```

MongoDB filters **and** returns results already sorted.

---

## Prefix Rule

Compound indexes work from **left to right**.

Index:

```js
{
    owner:1,
    createdAt:-1
}
```

Works for

```js
{ owner }
```

```js
{ owner, createdAt }
```

Does **not** efficiently support

```js
{ createdAt }
```

---

## ESR Rule (Design Rule)

Design compound indexes in this order:

```text
Equality → Sort → Range
```

Example

```js
Video.find({
    owner:userId,
    isPublished:true,
    views:{ $gt:100 }
}).sort({
    createdAt:-1
})
```

Index:

```js
{
    owner:1,
    isPublished:1,
    createdAt:-1,
    views:1
}
```

---

# Multikey Index

Used automatically for array fields.

Document

```js
{
    title:"MongoDB",
    tags:[
        "database",
        "backend",
        "nosql"
    ]
}
```

Index

```js
db.videos.createIndex({
    tags:1
})
```

MongoDB indexes every array element.

```text
backend → Doc1

database → Doc1

nosql → Doc1
```

Query

```js
Video.find({
    tags:"backend"
})
```

becomes fast.

=> Let's understand why a **Multikey Index** makes queries faster:

## 1. WITHOUT an Index: Full Collection Scan (`COLLSCAN`)

If you have 1,000,000 videos in your collection and run:
`Video.find({ tags: "backend" })`

MongoDB has to open every single document on the disk, expand its `tags` array, and check if `"backend"` exists inside it.

### Figure 1: The Slow Way (Checking 1 Million Docs)

```text
               +------------------------------------------------------+
               |                 MongoDB Collection                   |
               +------------------------------------------------------+
                                          |
    [Doc 1]    { title: "MongoDB", tags: ["database", "backend", "nosql"] }
               ---> Open Doc -> Scan Array -> MATCH! (Save Doc 1)
                                          |
    [Doc 2]    { title: "React",   tags: ["frontend", "ui"] }
               ---> Open Doc -> Scan Array -> NO MATCH (Skip)
                                          |
    [Doc 3]    { title: "NodeJS",  tags: ["backend", "javascript"] }
               ---> Open Doc -> Scan Array -> MATCH! (Save Doc 3)
                                          |
       ... (Repeats for all 1,000,000 documents) ...

    TIME COMPLEXITY: O(N) — Scans 1,000,000 items

```

## 2. WITH a Multikey Index: Index Scan (`IXSCAN`)

When you create the index using `db.videos.createIndex({ tags: 1 })`, MongoDB automatically detects that `tags` is an array.

Instead of creating **one** index entry per document, it creates **multiple index keys**—one entry for *every single element* inside the array. This is why it is called a **Multikey** index.

### Figure 2: How MongoDB Builds the Multikey Index

```text
Document 1: { _id: 1, tags: ["database", "backend", "nosql"] }
Document 3: { _id: 3, tags: ["backend", "javascript"] }

                     Multikey Index Table (Sorted B-Tree)
                     +---------------+------------------+
                     | Index Key     | Document Pointer |
                     +---------------+------------------+
                     | "backend"     | Doc 1, Doc 3     |  <-- Points to both!
                     | "database"    | Doc 1            |
                     | "javascript"  | Doc 3            |
                     | "nosql"       | Doc 1            |
                     +---------------+------------------+

```

## 3. How the Query Executes with the Index

When you execute `Video.find({ tags: "backend" })`, MongoDB bypasses scanning the raw documents entirely at first.

### Figure 3: The Fast Way (Direct B-Tree Lookup)

```text
Query: Find "backend"
       |
       v
+-------------------------------------------------------+
|                 Sorted Index B-Tree                   |
|  "ai"  -->  "backend"  -->  "css"  -->  "database" ... |
+-------------------------------------------------------+
                   |
                   +-- Binary Search finds "backend" in O(log N) steps!
                   |
                   v
      Index returns pointers: [ Doc 1, Doc 3 ]
                   |
                   v
+-------------------------------------------------------+
|  MongoDB fetches ONLY Doc 1 and Doc 3 from disk       |
+-------------------------------------------------------+

TIME COMPLEXITY: O(log N) — Instant search in a sorted structure

```

# Index Tradeoffs

### ✅ Faster Reads

Avoids expensive collection scans.

---

### ❌ Slower Writes

Every insert/update must also update every affected index.

```text
Insert Document

↓

Update Collection

↓

Update Owner Index

↓

Update Title Index

↓

Update CreatedAt Index
```

More indexes = slower writes.

---

### ❌ More Storage

Example

```text
Collection : 20 GB

Indexes   : 12 GB
```

Indexes consume RAM and disk.

---

### ❌ Maintenance

Changing an indexed field also updates the index.

---

# System Design Mindset

Don't ask:

> "Should I index this field?"

Ask:

> "Will this field be queried frequently?"

Example

```js
Video.find({
    owner:userId
})
```

Used thousands of times?

✅ Index it.

---

```js
Video.find({
    createdAt:"2026-01-01"
})
```

Rarely queried?

❌ Don't index it just because it exists.

---

# Real Example (YouTube Homepage)

Query

```js
Video.find({
    isPublished:true
})
.sort({
    createdAt:-1
})
.limit(20)
```

Index

```js
{
    isPublished:1,
    createdAt:-1
}
```

MongoDB can:

* Filter
* Sort
* Return first 20 documents

using only the index.

---

# Backend Rules

✅ Index fields used in:

* `find()`
* `$match`
* `sort()`
* Frequent joins (`$lookup` join keys)
* Pagination

Avoid indexing fields that:

* Are rarely queried.
* Have very low selectivity when used alone (e.g., a boolean field by itself).
* Change very frequently unless the read performance benefit outweighs the write cost.

---

# Key Takeaways

* **Single Index:** One field.
* **Compound Index:** Multiple fields (follow **ESR** and **Prefix Rule**).
* **Multikey Index:** Arrays.
* Indexes speed up **reads** but slow **writes** and consume storage.
* Design indexes based on **query patterns**, not on how many fields a collection has.
